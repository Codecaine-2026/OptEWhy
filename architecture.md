# AI-Driven Causal Reasoning & Scenario Simulation Platform for Port Operations

## 1. Architecture Goals

This platform is designed as a causal decision-support system for port operations. It should answer operational questions that ordinary dashboards cannot answer:

- What is happening now?
- Why is it happening?
- Which causal paths or feedback loops are driving the issue?
- What will happen if an operator changes a policy, resource, or subsystem condition?
- Which intervention is expected to create the best system-wide outcome?

The core design principle is separation of responsibilities:

- The Dynamic FCM engine performs causal computation.
- The RAG layer retrieves operational evidence.
- The LLM translates user intent and explains validated results.
- The UI visualizes causal structure, contribution, uncertainty, and scenario propagation.

The LLM must not be the source of causal truth. It should only orchestrate, translate, and explain outputs generated by deterministic or model-governed backend services.

### 4.2 FCM Node Types

Each FCM node should represent a measurable operational state or KPI.

| Node Type | Examples | Expected Data |
| --- | --- | --- |
| State KPI | Yard Density, Berth Occupancy, Gate Queue | Time-series metrics |
| Performance KPI | QC Productivity, Truck Turn Time, Vessel Turnaround Time | Time-series metrics |
| Resource Availability | QC Availability, RTG Availability, Labor Availability | Event and status records |
| Delay Factor | QC Waiting, Retrieval Delay, Dispatch Delay | Derived metrics |
| External Context | Weather Severity, Vessel Arrival Delay, Traffic Condition | External feeds |
| Intervention Variable | Add QC, Move Containers, Change Dispatch Rule | Scenario input |

### 4.3 FCM Edge Model

Each edge describes directional causal influence between two nodes.

```json
{
  "id": "edge_yard_density_to_truck_travel_time",
  "sourceNodeId": "yard_density",
  "targetNodeId": "internal_truck_travel_time",
  "baseWeight": 0.78,
  "polarity": "positive",
  "lagMinutes": 15,
  "confidence": 0.82,
  "evidenceLevel": "expert_and_data",
  "subsystem": "yard_to_transport",
  "dynamicWeightModelId": "weight_model_yard_transport_v1"
}
```

Important fields:

- `baseWeight`: Default causal influence in the range `[-1, 1]`.
- `polarity`: Positive or negative effect direction.
- `lagMinutes`: Expected delay before the source affects the target.
- `confidence`: Confidence in the causal edge.
- `evidenceLevel`: Source of validation, such as expert-only, data-supported, or intervention-validated.
- `dynamicWeightModelId`: Optional model that calculates context-specific weight.

## 5. Data Architecture

### 5.1 Data Sources

Operational data should be ingested from these source categories:

- TOS: vessel calls, moves, berth plans, yard inventory, dispatch jobs.
- IoT / telemetry: equipment status, GPS, crane events, sensor values.
- Maintenance systems: faults, downtime, planned maintenance, repair notes.
- Gate systems: external truck arrivals, queue length, transaction times.
- Workforce systems: shift, gang, skill availability.
- External feeds: weather, road traffic, vessel ETA updates.
- Documents: SOPs, incident reports, maintenance reports, shift reports, yard planning guidelines.

### 5.2 Storage Design

| Storage | Recommended Use | Candidate Technology |
| --- | --- | --- |
| Relational DB | Entities, users, scenarios, audit logs | PostgreSQL |
| Time-Series Store | KPI history, sensor states, event aggregates | TimescaleDB or ClickHouse |
| Graph Store | FCM graph, hierarchy, causal paths | Neo4j or PostgreSQL graph tables |
| Vector Store | RAG document chunks and embeddings | pgvector, Qdrant, or Weaviate |
| Object Storage | Raw reports, uploaded files, model artifacts | S3-compatible storage |
| Cache | Current state snapshots, hot graph queries | Redis |

For a prototype, PostgreSQL with TimescaleDB and pgvector is enough. A separate graph database can be introduced later if graph traversal workloads become heavy.

### 5.3 Current State Snapshot

The causal engine should not query raw operational tables directly for every analysis. A Current State Engine should produce normalized snapshots.

```json
{
  "snapshotId": "snap_2026_08_18_shift_a_001",
  "terminalId": "terminal_alpha",
  "timeWindow": {
    "start": "2026-08-18T08:00:00+09:00",
    "end": "2026-08-18T09:00:00+09:00"
  },
  "entities": {
    "vesselId": "vessel_a",
    "berthId": "berth_2",
    "yardBlocks": ["block_b", "block_c"]
  },
  "nodeValues": {
    "yard_density_block_b": 0.85,
    "yard_density_block_c": 0.82,
    "internal_truck_travel_time": 0.71,
    "qc_waiting": 0.64,
    "qc_productivity": -0.15
  }
}
```

Node values should be normalized before FCM computation. A common convention is `[-1, 1]`, where `0` means normal baseline, positive means above baseline, and negative means below baseline.

## 6. Intelligence Layer

### 6.1 Dynamic FCM Engine

The Dynamic FCM engine owns causal computation.

Responsibilities:

- Load the relevant causal graph for a terminal, subsystem, entity, or scenario.
- Calculate context-aware edge weights.
- Propagate state changes through the graph.
- Estimate contribution of paths and nodes to a target KPI.
- Detect dominant causal paths.
- Detect reinforcing and balancing feedback loops.
- Run counterfactual scenario simulations.
- Return machine-readable results with confidence and uncertainty.

Core formula:

```text
X(t + 1) = activation(X(t) × W(context_t))
```

Where:

- `X(t)` is the current normalized node state vector.
- `W(context_t)` is the context-specific causal weight matrix.
- `activation` constrains values to a stable range, such as `tanh`, sigmoid, or clipped linear activation.

### 6.2 Dynamic Weight Learning

Static causal weights are insufficient for congestion-heavy port operations. Dynamic weights should be generated by a model:

```text
W_ij(t) = f(source_node, target_node, system_context_t)
```

Recommended context features:

- Yard density.
- Vessel workload.
- Berth occupancy.
- Equipment availability.
- Truck utilization.
- Shift and time of day.
- Weather severity.
- Gate arrival pattern.
- Historical congestion regime.

Implementation options:

| Phase | Method | Reason |
| --- | --- | --- |
| Prototype | Rule-based regime weights | Easy to validate with domain experts |
| MVP | Gradient boosted model per edge group | Strong tabular performance and explainability |
| Advanced | Neural dynamic weight model | Better nonlinear modeling across many contexts |
| Research | Hybrid causal inference + FCM calibration | Stronger causal validity |

### 6.3 Causal Path Contribution

For a target KPI anomaly, the engine should identify paths that explain the observed change.

Example output:

```json
{
  "targetNodeId": "qc_productivity",
  "observedDelta": -0.14,
  "dominantPaths": [
    {
      "path": [
        "yard_density",
        "internal_truck_travel_time",
        "qc_waiting",
        "qc_productivity"
      ],
      "contributionRatio": 0.46,
      "signedImpact": -0.064,
      "confidence": 0.78
    }
  ],
  "residualRatio": 0.08
}
```

Path contribution should account for:

- Edge weights.
- Current node abnormality.
- Lag compatibility.
- Path length penalty.
- Confidence penalty.
- Competing path overlap.

### 6.4 Feedback Loop Detection

Feedback loops should be classified into:

- Reinforcing loops: amplify the current system state.
- Balancing loops: counteract the current system state.

Loop strength can be estimated from:

```text
loop_strength = product(edge_weights) × average(node_abnormality) × confidence_factor
```

Example:

```text
Yard Density
→ Rehandling Rate
→ RTG Workload
→ Retrieval Time
→ Truck Congestion
→ Yard Density
```

The UI should highlight loops only when their contribution passes a configurable threshold. This prevents visual overload.

### 6.5 Scenario Simulation

Scenario simulation should be implemented as a controlled intervention.

Scenario request:

```text
Move 15% of Block B containers to Block D.
```

Structured intervention:

```json
{
  "scenarioId": "scenario_move_block_b_to_d",
  "interventions": [
    {
      "nodeId": "yard_density_block_b",
      "operation": "decrease_relative",
      "value": 0.15
    },
    {
      "nodeId": "yard_density_block_d",
      "operation": "increase_relative",
      "value": 0.11
    }
  ],
  "simulationHorizonMinutes": 180,
  "propagationSteps": 12
}
```

Expected response:

```json
{
  "summary": {
    "qc_productivity": 0.037,
    "vessel_turnaround_time_minutes": -19,
    "gate_retrieval_time": 0.02
  },
  "propagation": [
    {
      "step": 1,
      "nodeImpacts": {
        "yard_density_block_b": -0.13,
        "rehandling_rate": -0.08
      }
    }
  ],
  "warnings": [
    "Block D density increase may raise gate retrieval time by approximately 2%."
  ]
}
```

## 7. RAG Evidence Engine

The RAG engine supports causal reasoning with operational evidence. It should not replace the causal engine.

Responsibilities:

- Ingest operational documents.
- Chunk documents by operational event, equipment, vessel, time range, and subsystem.
- Retrieve evidence relevant to an entity, KPI, time window, and causal path.
- Return citations and structured metadata.

Recommended document metadata:

```json
{
  "documentId": "maintenance_qc4_2026_08_18",
  "documentType": "maintenance_report",
  "terminalId": "terminal_alpha",
  "entityType": "equipment",
  "entityId": "qc4",
  "timeStart": "2026-08-18T06:30:00+09:00",
  "timeEnd": "2026-08-18T07:50:00+09:00",
  "subsystem": "quay",
  "tags": ["qc4", "availability", "fault", "hydraulic_alarm"]
}
```

Example retrieval target:

```json
{
  "question": "Why did QC4 affect productivity today?",
  "entityIds": ["qc4", "vessel_a"],
  "timeWindow": {
    "start": "2026-08-18T00:00:00+09:00",
    "end": "2026-08-18T12:00:00+09:00"
  },
  "causalPath": [
    "qc4_failure",
    "qc_availability",
    "qc_productivity",
    "vessel_turnaround_time"
  ]
}
```

## 8. LLM Orchestration

The LLM layer converts between natural language and structured system actions.

### 8.1 Intent Types

| Intent | Example | Backend Action |
| --- | --- | --- |
| Anomaly explanation | "Why is Vessel A productivity low?" | Causal path analysis + RAG evidence |
| Root mechanism analysis | "What is causing Yard Block C congestion?" | Dominant path + loop detection |
| Scenario simulation | "What if we add one QC?" | Intervention translation + simulation |
| Counterfactual | "Would the delay still happen if QC4 was normal?" | Counterfactual state override |
| Recommendation | "How can we reduce turnaround?" | Candidate scenario ranking |
| Evidence lookup | "Show reports related to QC4." | RAG retrieval |

### 8.2 Structured Query Contract

```json
{
  "intent": "anomaly_explanation",
  "target": {
    "nodeId": "qc_productivity",
    "entityType": "vessel",
    "entityId": "vessel_a"
  },
  "timeWindow": {
    "mode": "current_shift"
  },
  "analysisOptions": {
    "includePaths": true,
    "includeLoops": true,
    "includeEvidence": true,
    "includeRecommendations": false
  }
}
```

### 8.3 Explanation Rules

Generated explanations should always include:

- The main causal mechanism.
- The top contributing paths with percentages.
- Supporting operational evidence when available.
- Confidence or uncertainty.
- Any important tradeoff or side effect.
- A clear distinction between observed facts, model estimates, and retrieved document evidence.

Generated explanations should avoid:

- Presenting correlation as confirmed causality.
- Inventing missing evidence.
- Hiding uncertainty.
- Performing causal computation inside the LLM prompt.

### 10.3 Graph Visualization Rules

- Node color represents current abnormality.
- Edge thickness represents absolute causal weight.
- Edge color represents positive or negative influence.
- Highlight intensity represents contribution to the selected target KPI.
- Low-contribution nodes and edges should fade to lower opacity.
- Feedback loops should be visually distinct from linear paths.
- The default view should show the most relevant subgraph, not the entire port graph.
- System-wide propagation should be available as an explicit mode.

Recommended graph stack:

- Prototype: React Flow or Cytoscape.js.
- Advanced large graph: Sigma.js or custom WebGL graph rendering.
- Scenario animation: deterministic propagation frames from the backend.

## 11. Backend Services

### 11.1 API Gateway

Responsibilities:

- Authentication and authorization.
- Request validation.
- Rate limiting.
- Tenant and terminal isolation.
- Streaming responses for long-running analysis.
- Routing to application services.

### 11.2 Query Orchestrator

Responsibilities:

- Accept user query.
- Ask LLM to produce structured query.
- Resolve entities, time windows, and target KPIs.
- Request current state snapshot.
- Run causal analysis.
- Retrieve evidence.
- Build final response.
- Return visualization instructions.

### 11.3 Scenario Orchestrator

Responsibilities:

- Parse scenario from natural language or structured form.
- Validate intervention feasibility.
- Apply intervention to state snapshot.
- Run propagation simulation.
- Compare baseline and scenario outputs.
- Identify expected side effects.
- Store scenario for review and comparison.

### 11.4 Model Management Service

Responsibilities:

- Store calibrated FCM weights.
- Store dynamic weight model versions.
- Track training data windows.
- Track validation metrics.
- Support rollback to previous models.
- Provide model metadata to explanations.

## 12. Model Development Roadmap

### Phase 1: Expert-Based FCM

Objective:

- Build the initial causal graph from expert interviews and operational knowledge.

Deliverables:

- Node catalog.
- Edge catalog.
- Initial static weights.
- Confidence levels.
- Subsystem hierarchy.
- Basic path and loop visualization.

### Phase 2: Data-Driven Weight Calibration

Objective:

- Fit FCM weights using historical operational data.

Deliverables:

- Historical KPI dataset.
- Normalization pipeline.
- Weight calibration jobs.
- Prediction error metrics.
- Expert review workflow.

### Phase 3: Dynamic Weight Learning

Objective:

- Make causal weights context-aware.

Deliverables:

- Context feature store.
- Regime detection.
- Dynamic weight models.
- Congestion threshold behavior.
- Model versioning.

### Phase 4: Causal Validation

Objective:

- Reduce the risk of treating correlation as causality.

Deliverables:

- Historical intervention analysis.
- Natural experiment review.
- Causal inference checks.

## 18. Key Design Decisions

1. Use a Dynamic FCM as the causal computation core.
2. Keep the LLM outside the causal calculation path.
3. Represent every answer as structured analysis first, natural language second.
4. Use RAG only for operational evidence and document context.
5. Normalize operational KPI states before FCM computation.
6. Start with expert weights, then calibrate with historical data.
7. Make scenario simulation deterministic and auditable.
8. Show focused subgraphs by default to avoid overwhelming operators.
9. Track model versions, data snapshots, and evidence sources for every answer.
10. Treat intervention recommendations as decision support, not automatic control.
